# OCR Playground

한글 문서·스캔본을 넣으면 **줄 단위 텍스트 + 위치 + 신뢰도**를 그대로 보여주는 최소 OCR 앱.
AX 아이디어를 얹기 전에, 기본 OCR이 어디까지 되고 어디서 깨지는지 눈으로 확인하려고 만든 기준선(baseline)이다.

```
ocr-ai/
├── backend/     FastAPI + RapidOCR (ONNX Runtime, CPU)
├── frontend/    Next.js 16 + React 19 + Tailwind v4
└── docs/        트러블슈팅 기록
```

만들면서 실제로 부딪힌 문제와 해결 과정은
**[docs/troubleshooting/](docs/troubleshooting/README.md)** 에 건별로 정리해 뒀다.
시도했지만 안 된 방법과 그 이유까지 남겨 놨다.

## 스택 선택 이유

| 선택 | 이유 |
| --- | --- |
| **RapidOCR 3.x (ONNX Runtime)** | PaddleOCR 모델(PP-OCRv5 한국어)을 ONNX로 돌려서 `torch`·`paddle` 없이 CPU만으로 동작. 설치 200MB 미만, 첫 로딩 5초, 추론 1~4초 |
| **PP-OCRv6 det + PP-OCRv5 korean rec** | 검출은 최신 v6, 한국어 인식 모델은 v5가 최신 |
| **FastAPI + Pydantic v2** | 응답 스키마가 곧 계약. `/docs`에서 바로 테스트 가능 |
| **Next.js App Router + React 19** | 결과 시각화(박스 오버레이 ↔ 텍스트 연동)가 핵심이라 클라이언트 렌더링 |
| **Tailwind v4** | `@theme` CSS 변수 기반, 설정 파일 없음 |

## 실행

터미널 2개가 필요하다.

```bash
cd backend && ./.venv/bin/python -m uvicorn app.main:app --reload --port 8000
```

```bash
cd frontend && npm run dev
```

→ http://localhost:3000

첫 실행 때 한국어 인식 모델(13MB)을 자동으로 내려받는다. API 문서는 http://127.0.0.1:8000/docs.

### 처음부터 세팅할 때

```bash
cd backend && python3.13 -m venv .venv && ./.venv/bin/pip install -e . && cd ../frontend && npm install
```

## 기능

- 드래그&드롭 · 파일 선택 · **클립보드 붙여넣기(⌘V)** · PDF(최대 5쪽)
- **PDF 텍스트 레이어 우선** — 글자가 들어 있는 PDF는 OCR을 건너뛴다 (아래 참고).
  418배 빠르고 인식 오류가 없다. 스캔 PDF는 자동으로 OCR로 폴백
- 이미지 위에 검출 영역 오버레이 — 신뢰도에 따라 초록/노랑/빨강
- 박스 ↔ 텍스트 줄 **양방향 하이라이트**(호버·클릭 시 목록 자동 스크롤)
- **띄어쓰기 복원** — 인식 모델이 흘린 공백을 원본 픽셀 기준으로 되살림 (아래 참고)
- **레이아웃 분석** — 좌표로 단·표를 복원하고 읽는 순서를 잡음 (아래 참고).
  이미지 오버레이를 `줄 / 블록`으로 전환해 블록·셀 경계를 확인할 수 있다
- **항목 추출** — Claude로 "합계금액 → 17,160,000" 같은 의미 단위 추출 (아래 참고).
  각 값의 **근거 줄**을 함께 받아 이미지에서 원본 위치를 짚어준다
- **입력 품질 경고** — 결과를 믿어도 되는지 미리 알려준다 (아래 참고)
- 줄 단위 / 레이아웃 / 항목 추출 / 전체 텍스트 / JSON 5개 뷰, 복사 및 `.txt` `.md` `.json` 내려받기
- 단계별 소요 시간(검출·방향보정·인식·띄어쓰기·레이아웃), 평균 신뢰도, 확인 필요 줄 수
- 언어 전환(한국어/영어/중국어/일본어/라틴)

## API

```
POST /api/ocr      multipart: file, lang=korean, use_angle_cls=false,
                              restore_spacing=true, analyze_layout=true, force_ocr=false
POST /api/extract  json: { lines, markdown, preset }   ← LLM 항목 추출
GET  /api/health
```

응답 구조:

| 필드 | 내용 |
| --- | --- |
| `lines[]` | 줄 단위. `polygon`(4점 다각형), `bbox`, `confidence`, `page`, `block_id`, `reading_index` |
| `lines[].raw_text` | 띄어쓰기 복원 전 원본. 비교용 |
| `blocks[]` | 레이아웃 블록. `kind`(text/table), `page_column`, `bbox`, `cells[]`(row·column·text·bbox) |
| `full_text` | **읽는 순서대로** 정렬된 텍스트 |
| `raw_text` | 검출 순서 그대로 + 띄어쓰기 복원 전 |
| `markdown` | 표를 파이프 표로 살린 마크다운. LLM에 그대로 넘기기 좋다 |
| `quality` | `level`(good/fair/poor), 평균 신뢰도, 글자 높이 중앙값, 사람이 읽을 경고 |
| `pages[].source` | `pdf_text`면 OCR 없이 PDF 텍스트 레이어에서 읽은 것 |

`blocks[].cells`에 행·열 인덱스와 좌표가 다 들어 있어 항목 추출(Key-Value)을 붙이기 좋다.

## 만들면서 확인한 baseline 성능

`frontend/public/sample.png`(1240×1600, 0.7° 기울인 거래명세서) 기준:

- 39줄 전부 검출, 텍스트 오인식 0건, 평균 신뢰도 0.98
- 소요 2.5초 (검출 1.1s / 인식 1.4s, M-series CPU)

### 짚고 넘어간 이슈: 각도 분류기(`use_angle_cls`)는 기본 off

RapidOCR 기본값은 각도 분류기가 켜져 있는데, 이 모델(`ch_ppocr_mobile_v2.0_cls`)은 중국어
기준이라 **똑바로 놓인 한글 줄을 180도 뒤집힌 것으로 오판**한다. 샘플에서 실제로 이렇게 깨졌다.

| | 켰을 때 | 껐을 때 |
| --- | --- | --- |
| 검출 줄 수 | 35 | **39** |
| 신뢰도 0.9 미만 | 2줄 | **0줄** |
| `거래명세서` | `FY IY H H` | `거래명세서` |
| `부가세(10%)` | `(%OL)\|Y∠` | `부가세(10%)` |

그래서 기본값을 껐고, 화면 우상단 **"회전 보정"** 체크박스로 켜서 차이를 직접 볼 수 있게 뒀다.
뒤집힌 스캔을 다뤄야 할 때만 켜면 된다.

## 띄어쓰기 복원 (`backend/app/spacing.py`)

PP-OCR 인식 모델은 글자는 잘 맞히면서 공백을 자주 흘린다.
`·결제조건:세금계산서발행일로부터30일이내`, `테헤란로152,8층` 처럼.

**한국어 띄어쓰기 교정기(Kiwi 등)로는 못 푼다.** 실제로 붙여서 확인한 결과,
문서에 없던 공백까지 넣어 복합명사를 다 쪼개버린다:

```
거래명세서         -> 거래 명세서
문서번호           -> 문서 번호
부가세(10%)        -> 부가세(10 %)
(주)에이엑스솔루션  -> (주)에이 엑스 솔루션
```

문서 OCR에서 원하는 건 "문법적으로 옳은 띄어쓰기"가 아니라 **원본에 있던 공백**이다.
그래서 언어 모델 대신 원본 픽셀을 직접 본다.

1. 검출된 줄 다각형을 똑바로 편 크롭으로 만든다 (기울어진 스캔 대응)
2. Otsu 이진화 후 열 방향 잉크 투영으로 획이 하나도 없는 열 구간을 찾는다
3. 그중 폭이 중앙값의 2배 이상인 구간만 단어 사이 공백으로 인정한다
4. 인식 결과의 글자 박스(`return_single_char_box`)와 대조해 몇 번째 글자 앞인지 정하고 넣는다

인식 결과에 이미 있는 공백은 건드리지 않고 없는 자리에만 추가한다.
자간을 넓힌 제목(`거 래 명 세 서`)은 모든 글자가 떨어져 있으므로, 검출된 공백 수가
글자 수와 같으면 단어 구분이 아니라고 보고 건너뛴다.

### 결과

샘플 39줄 중 8줄이 복원됐고 **전부 원본 문구와 정확히 일치**한다. 오삽입 0건.

```
2026년8월 16일               -> 2026년 8월 16일
문서 OCR 엔진라이선스(연간)   -> 문서 OCR 엔진 라이선스 (연간)
업무 자동화 컨설팅(40시간)    -> 업무 자동화 컨설팅 (40시간)

·결제조건:세금계산서발행일로부터30일이내 현금 지급
  -> · 결제조건: 세금계산서 발행일로부터 30일 이내 현금 지급
·납품장소: 서울특별시 강남구 테헤란로152,8층
  -> · 납품장소: 서울특별시 강남구 테헤란로 152, 8층
```

건드리지 않은 것: `거래명세서`, `문서번호`, `공급가액`, `합계금액`, `부가세(10%)`,
`한국디지털전환 주식회사` — 원본에 공백이 없으니 그대로 둔다.

글꼴 크기·노이즈를 섞은 별도 테스트에서도 오삽입은 없었다.
비용은 39줄에 **6~20ms** (전체 2.5초 중). `return_single_char_box`를 켠 데 따른
인식 속도 저하는 측정되지 않았다(2617ms → 2597ms).

우상단 **"띄어쓰기 복원"** 체크박스를 끄면 원본 인식 결과가 나오고, 켜져 있을 때
바뀐 줄은 목록에 `띄어쓰기 복원` 배지와 함께 원본이 같이 표시된다.

### 한계

- 원본에도 공백이 없으면 복원할 게 없다. `띄어쓰기가전혀없는문장`은 그대로 남는다
  → 문법 기반 교정이 필요한 영역(LLM 후처리 대상)
- 글자가 붙어 인쇄된 저해상도 스캔은 잉크 투영이 뭉개져 효과가 떨어진다
- 세로쓰기는 대상이 아니다

## 레이아웃 분석 — 읽는 순서와 표 구조 (`backend/app/layout.py`)

검출 결과는 줄 텍스트가 검출 순서대로 나열된 것뿐이라 2단 편집이면 좌우가 섞이고,
표는 `품목 / 수량 / 단가 / 금액`이 각각 별개 줄로 흩어져 셀 관계가 없다.
읽는 순서와 표 구조는 같은 기반(행 밴딩 + 열 클러스터링) 위에 있어서 한 모듈에서 같이 푼다.

### 절차

1. **영역 나누기 (XY-cut)** — 세로 여백으로 단을 가르고, 안 되면 가로 여백으로 자르고 반복
2. **행 묶기** — 세로로 겹치는 줄들을 한 행(band)으로
3. **표 영역 찾기** — 행을 하나씩 얹으면서 열 구조가 유지되는 동안 표를 키움
4. **열 나누기** — 표 안에서 x 구간이 겹치는 셀끼리 같은 열로
5. **줄바꿈된 셀 합치기** — 첫 열을 차지하는 밴드만 행으로 보고, 나머지는 가까운 행에 붙임
6. **읽는 순서** — 단 → 위에서 아래 → 표 안에서는 왼쪽에서 오른쪽

### 여기서 어려운 부분

**세로 여백만 보고 단을 가르면 표가 통째로 쪼개진다.** 표의 열 사이도 똑같은 세로 여백이다.
반대로 페이지 전체에서만 여백을 찾으면, **가운데 정렬된 제목 한 줄이 단 사이를 가로질러서
2단 편집을 통째로 놓친다.** 실제로 2단 테스트 문서에서 제목 하나 때문에 좌우가 한 덩어리로
묶이고, 문단이 `2×2 표`로 오인됐다.

그래서 세로 절단에 "단처럼 보이는가" 조건을 붙였다:

| 조건 | 걸러내는 것 |
| --- | --- |
| 각 단에 줄이 3개 이상 | 우연히 생긴 여백 |
| 각 단이 영역 높이의 60% 이상 차지 | 표의 열 (대부분 여기서 걸린다) |
| 각 단의 줄 길이 중앙값 ≥ 8자 | `수량`·`금액` 같은 짧은 열 |
| **단 폭 차이가 1.8배 이내** | **라벨 열이 긴 표** (아래 참고) |
| 여백을 가로지르는 줄이 8% 이하 | — |
| 가로지르는 줄은 영역 너비의 20% 이상 | 우연히 걸친 짧은 줄 |

**단 폭 조건이 없으면 표가 세로로 두 동강 난다.** `기밀성(Confidentiality)`처럼 라벨이
길면 "줄 길이 ≥ 8자" 조건을 통과해 버려서, 라벨 열과 내용 열이 각각 하나의 단이 된다.

```
단0: 구분 / 기밀성(Confidentiality) / 무결성(Integrity) / ...
단1: 개념 / 오직 인가된 사람 ... / 정보의 내용이 ... / ...
```

2단 편집은 **설계상 단 폭이 거의 같은** 반면(테스트 문서 325px vs 316px = 1.03배),
표는 라벨 열이 내용 열보다 훨씬 좁다(157px vs 550px = 3.50배). 이걸로 갈린다.

여백을 가로지르는 줄(가운데 정렬 제목 등)은 **구분선**으로 따로 빼서, 그 위아래로 단을 나눠
읽는다. 이걸 넣고서야 2단 문서가 `제목 → 좌단 전체 → 우단 전체`로 제대로 읽혔다.

### 줄바꿈된 셀 — 실제 교재로 테스트하다 잡은 문제

처음에는 표 구간을 "셀 개수가 같은 연속된 행"으로 잡았다. 실제 교재 페이지를 넣어 보니
**6행짜리 표가 2행으로 쪼그라들었다.** 셀 내용이 두 줄로 넘어가는 행이 있으면 그 행만 줄 수가
달라져서, 거기서 표가 끊긴 것이다.

```
구분   | 개념
기밀성 | 오직 인가된 사람 ... 시스템에 접근     ← 두 줄짜리 셀
       | 해야 한다는 원칙
무결성 | 정보의 내용이 ...                      ← 한 줄짜리 셀
```

그래서 판정 기준을 **셀 개수**에서 **열 구조가 유지되는가**로 바꿨다. 한 열에 여러 줄이
들어와도 가로로 겹치면 줄바꿈된 같은 셀이고, 가로로 떨어져 있으면 새 표가 시작된 것이다.

여기에 더해, 해상도가 높아지면 **항목 이름이 세로 가운데 정렬이라 첫 줄이 아니라 가운데 줄과
겹친다.** 그래서 이어지는 줄이 행보다 위에 올 수도 있고 아래에 올 수도 있다.

```
기밀성 행의 실제 좌표 (1224px 렌더 기준)
  "오직 인가된 ..."   y 310~327   ← 이름과 안 겹침
  "기밀성(...)"        y 330~348
  "해야 한다는 원칙"   y 338~355   ← 이름과 겹침
```

그래서 **첫 열을 차지하는 밴드만 행으로 보고, 나머지는 세로로 더 가까운 행에 붙인다.**
위/아래 어느 쪽이든 대응된다. 셀 안에서는 y로 정렬해 원래 문장 순서를 복구하는데,
검출기가 한 줄을 둘로 쪼개는 경우가 있어 y 차이가 줄 높이의 70% 안이면 x 순으로 읽는다.

"첫 열이 비고 여러 열에 걸친 행"은 줄바꿈이 아니라 새 표로 본다.
거래명세서에서 품목 표 아래의 합계 표(`공급가액 | 15,600,000`)가 이 규칙으로 분리된다.

### 결과

거래명세서 샘플 — 블록 7개, 표 3개, `layout_ms: 1~2ms`:

```
[본문]  거래명세서
[표 5×2] 문서번호 | AX-2026-0817-013 ...        (머리글 없음: 항목-값 표)
[표 4×4] 품목 | 수량 | 단가 | 금액 ...           (머리글 있음)
[표 3×2] 공급가액 | 15,600,000 ...
[본문]  [특기사항] · 결제조건 ... · 납품장소 ...
[본문]  위와 같이 거래 내역을 확인합니다.
[본문]  (주)에이엑스솔루션 (인)
```

머리글 판정은 두 신호를 본다. `"수량 / 1 / 40 / 1"`처럼 **첫 칸만 글자이고 아래가 숫자로
채워진 열**이 있거나, `"구분 / 기밀성(Confidentiality) / 무결성(Integrity) ..."`처럼
**첫 행이 모든 열에서 아랫줄들보다 눈에 띄게 짧으면** 머리글로 본다.
`공급가액 | 15,600,000`은 둘 다 걸리지 않아 머리글이 아니다.

실제 교재 페이지(`기초강의.pdf` 1·3쪽) — 정보보호 목표 표가 `7×2`(머리글 포함 전 행),
접근통제 3단계 표가 `4×2`로 나온다. 두 표 모두 셀이 두세 줄로 넘어가는 행이 섞여 있다.

2단 테스트 문서 — `page_columns: 2`, 표 오인식 0개, 좌단 전체를 읽은 뒤 우단으로 넘어간다.

`markdown` 필드로 이런 게 나온다:

```markdown
| 품목 | 수량 | 단가 | 금액 |
| --- | --- | --- | --- |
| 문서 OCR 엔진 라이선스 (연간) | 1 | 8,400,000 | 8,400,000 |
| 업무 자동화 컨설팅 (40시간) | 40 | 150,000 | 6,000,000 |
| 온프레미스 설치 및 교육 | 1 | 1,200,000 | 1,200,000 |
```

## 괘선 검출 (`backend/app/rules.py`)

위까지가 좌표만 쓰는 부분이다. 표에 실제로 그어진 선을 검출해서 표 판정을 보강한다.

이진화는 Otsu를 쓰지 않는다. 한글 문서의 괘선은 **밝기 186~234짜리 1px 연한 회색**이라
(교재 PDF 1쪽 실측, 배경 255) Otsu 임계값이 배경 쪽으로 밀어낸다. 대신 "배경 중앙값보다
12 이상 어두운가"로 잡고, 가로로 긴 커널로 opening을 걸어 글자를 지운다.

```
             Otsu    배경 대비 -12
거래명세서      1개  →   5개
교재 1쪽        2개  →   9개
표만 크롭       0개  →   7개
```

**두께·길이 기준은 이미지 크기가 아니라 글자 높이다.** 변 대비로 걸었더니 양쪽에서
틀렸다 — 스캔본은 블러 때문에 1px 선이 10~15px로 퍼져서 두께 상한에 걸려 버려졌고,
857×292 크롭에서는 최소 길이가 43px밖에 안 돼서 한글 세로획이 세로선 70개로 잡혔다.

| 조건 | 값 | 걸러내는 것 |
| --- | --- | --- |
| 두께 ≤ 글자 높이 × 1.0 | 블러 괘선 0.75배 통과 | 머리글 색 배경 띠 (2.1배) |
| 길이 ≥ 글자 높이 × 3, 그리고 변의 15% | | 글자 획, 본문 밑줄 |

### 쓰는 곳은 한 군데다 — "괘선이 있으면 확실히 표"

**행 분할까지 괘선에 맡겨 봤더니 5개 표 중 4개가 나빠졌다.**

| 표 | 좌표 기반 (정답) | 괘선 기반 |
| --- | --- | --- |
| 교재 7×2 | 7행 | **6행** |
| 교재 4×2 | 4행 | **3행** |
| 거래명세서 4×4 | 4행 | **3행** |

머리글 행이 선이 아니라 **색 배경 띠**로 구분돼 있어서 그 경계에 괘선이 없다.
게다가 거래명세서 5×2 표는 괘선이 **0개**다 — 없다고 표가 아닌 게 아니다.

그래서 신호를 한 방향으로만 쓴다. 표 폭의 90% 이상을 덮는 가로 괘선이 **3개 이상**이면
4지선다 판정(내용 신호에 기대는 약한 근거)을 뒤집는다. 실측 분포에서 뽑은 값이다.

```
괘선 있는 표   3개 / 4개 / 6개 / 6개
괘선 없는 표   0개 / 1개
```

1~2로 내리면 상자 하나 두른 4지선다가 위아래 테두리만으로 표가 된다.
자세한 경위는 [13번 문서](docs/troubleshooting/13-괘선-검출을-행-분할에-쓰면-나빠진다.md).

비용은 페이지당 2~26ms다.

### 한계

좌표만으로 푸는 방식이라 임계값에 기댄다. 다음은 아직 못 한다.

- **셀 병합(rowspan/colspan)** — "첫 열이 비고 여러 열에 걸친 행"은 새 표로 보기 때문에,
  세로 병합된 셀이 있으면 표가 거기서 끊긴다
- **첫 열의 줄바꿈** — 이어지는 줄 판정이 "첫 열이 아닌 열"을 기준으로 해서,
  항목 이름 자체가 두 줄로 넘어가면 별도 행이 된다
- **괘선으로 행 나누기** — 선은 검출하지만(`app/rules.py`) 표 판정에만 쓴다.
  행 분할까지 맡겨 봤더니 5개 표 중 4개가 나빠졌다. 머리글 행이 선이 아니라
  색 배경 띠로 구분돼 있어서 경계에 괘선이 없다 ([13번](docs/troubleshooting/13-괘선-검출을-행-분할에-쓰면-나빠진다.md))
- **세로 괘선** — 한글 문서는 가로선만 긋는 관행이 흔하다. 교재 1쪽에서 가로 8개에
  세로 1개였고 그마저 표가 아니라 페이지 장식선이었다. 열은 여전히 좌표로 잡는다
- **좌우 정렬이 어긋난 표** — 열 배정은 x 구간 겹침이라, 셀이 들쭉날쭉하면 열이 밀린다
- **가로로 늘어선 도표** — `평문 → 암호화 → 암호문` 같은 흐름도 라벨은 좌표만 보면 표와
  구분되지 않는다. 한 행짜리는 본문으로 되돌리지만, 2행 이상이면 표로 잡힐 수 있다
- **선택지 판별** — 4지선다는 격자 배치가 표와 완전히 같아 좌표로는 구분되지 않는다.
  첫 열의 항목 번호(`①②③④`)로 걸러내고, 번호가 인식되지 않으면
  "앞에 물음표 문장 + 짧은 칸 + 값 반복"으로 보조 판별한다.
  둘 다 걸리지 않는 격자는 표로 잡힌다
- **단 밖의 꼬리말** — 2단 문서에서 왼쪽 아래 꼬리말은 왼쪽 단의 끝으로 읽힌다
- 임계값은 A4 인쇄물 기준으로 맞췄다. 명함·영수증처럼 비율이 다른 문서는 재조정이 필요하다

정확도를 더 올리려면 레이아웃 분석 모델(PP-Structure, LayoutLMv3 등)을 붙이는 게 맞다.
다만 지금 구조라면 `analyze_page()` 하나만 갈아끼우면 되고, 응답 스키마는 그대로 쓸 수 있다.

### 회귀 테스트

임계값에 기대는 코드라 한쪽을 고치면 다른 쪽이 깨지기 쉽다. 실제로 두 번 깨졌다.
그래서 좌표만 만들어서 돌리는 테스트를 붙여 뒀다 (이미지·모델 없이 즉시 실행).

```bash
cd backend && ./.venv/bin/python tests/test_layout.py
cd backend && ./.venv/bin/python tests/test_quality.py
cd backend && ./.venv/bin/python tests/test_pdftext.py
cd backend && ./.venv/bin/python tests/test_rules.py
```

- 라벨이 긴 표가 2단으로 잘리지 않는지
- 폭이 비슷한 진짜 2단은 그대로 나뉘는지
- 줄바꿈된 셀이 있어도 표가 안 끊기는지, 이어지는 줄이 올바른 행·순서로 붙는지
- 첫 열이 빈 행에서 새 표가 시작되는지
- 한 행짜리 도표 라벨이 표로 안 잡히는지

## PDF 텍스트 레이어 (`backend/app/pdftext.py`)

전자세금계산서·계약서·보고서처럼 프로그램이 만든 PDF에는 글자가 그대로 들어 있다.
그걸 이미지로 렌더해서 OCR하는 건 느리기만 하고 부정확하다.

| 입력 | 경로 | 시간 | 표 |
| --- | --- | --- | --- |
| 교재 PDF 3쪽 | `pdf_text` | **64.9ms** | `7x2` + `4x2` |
| 같은 파일 강제 OCR | `ocr` | 27,120ms | `7x2` + `2x2` + `4x2` |
| 스캔 PDF | `ocr` (자동 폴백) | 8,512ms | 정상 |

**418배** 차이에 내용도 더 정확하다 — OCR은 `인가된 프로세스 인가된`으로 쉼표를 놓치고
`해야 한다는원칙`으로 띄어쓰기를 붙이는데, 텍스트 레이어는 원본 그대로다.

### 그냥 텍스트를 뽑으면 안 된다

`get_text_range()`가 주는 줄은 표의 두 셀을 한 줄로 합쳐 버린다
(`기밀성(Confidentiality) 오직 인가된 사람...`). 레이아웃 분석이 "한 줄 = 한 셀"을
전제로 하니 표를 못 잡는다.

그래서 **문자별 좌표로 줄을 직접 재구성한다.** 임계값은 실제 문서의 간격 분포에서 뽑았다.

| | 중앙값 | 최대 |
| --- | --- | --- |
| 붙어 있는 글자 | 0.03 | 0.30 |
| 공백 하나 | 0.53 | — |
| 표 셀 경계 | — | 2.99 이상 |

0.30과 0.53 사이에서 공백을 넣고, 0.69와 2.99 사이에서 셀을 가른다.
좌표는 `loose=True`(폰트 라인박스)를 쓴다 — 기본값인 잉크 범위를 쓰면 쉼표에서 줄이 끊긴다.
자세한 과정은 [트러블슈팅 12번](docs/troubleshooting/12-PDF-텍스트-레이어에서-줄이-쪼개진다.md).

우상단 **"강제 OCR"** 체크박스로 같은 파일을 두 경로로 비교할 수 있다.

## 항목 추출 (`backend/app/extract.py`)

레이아웃까지는 좌표로 풀 수 있지만, "합계금액 → 17,160,000"처럼 **의미를 붙이는 건
좌표에 답이 없다.** 여기서 Claude를 쓴다.

```bash
export ANTHROPIC_API_KEY=sk-ant-...   # 이게 있어야 활성화된다
```

- 모델 `claude-opus-5`, 구조화 출력(`messages.parse` + Pydantic 스키마)으로 형식을 강제
- 프리셋 두 가지: **자동 판별**(항목을 모델이 정함) / **거래명세서·영수증**(품목 표까지 분리)
- 정책 거절 시 `fallbacks: "default"`로 자동 재시도. 계정에 이 베타가 없으면 한 번만
  실패하고 끄고 간다
- 응답에 토큰 수와 **요금(USD)** 을 같이 실어 준다. 실효성 판단에 필요하다

### 근거를 같이 받는 게 핵심

값만 받으면 맞는지 확인할 방법이 없다. 그래서 모든 항목에 **근거가 된 OCR 줄 번호**를
같이 받는다.

```json
{ "key": "합계금액", "value": "17,160,000", "line_ids": [32, 33], "confidence": "high" }
```

- 화면에서 항목에 마우스를 올리면 이미지의 해당 줄이 강조된다 — 사람이 즉시 대조할 수 있다
- 색인에 없는 줄 번호를 가리키면 **지어낸 값일 수 있다는 신호**다. 서버에서 걸러내고
  경고를 남긴다

값은 전부 문자열로 받는다. `"1,250,000원"`을 `1250000`으로 정규화하지 않는다 —
원문 표기를 보존해야 사람이 대조할 수 있고, 숫자 파싱은 후단에서 하면 된다.

## 저품질 입력 — 측정과 품질 경고 (`backend/app/quality.py`)

손글씨·그림자·저해상도가 미검증이라 열화 조건을 만들어 측정했다.
전체 표와 과정은 [트러블슈팅 11번](docs/troubleshooting/11-저품질-입력은-전처리로-못-고친다.md).

**기울기·그림자·접힘은 사실상 영향이 없다** (기울기 8°에서도 CER 0%).
결정적 변수는 **글자 크기와 선명도**다.

| 조건 (실제 교재 1쪽) | 평균 신뢰도 | 줄 CER |
| --- | --- | --- |
| 원본 | 0.949 | 0.0% |
| 축소 60% | 0.925 | 6.1% |
| 팩스본 | 0.895 | 12.6% |
| 휴대폰 사진 | 0.878 | 15.3% |
| 축소 40% | 0.824 | 22.7% |
| 흐림 r=2.0 | 0.801 | 31.6% |

**전처리로는 못 고친다.** 2배 확대는 개선이 없거나 악화(흐림: 31.6% → 40.3%),
언샤프 마스크는 네 조건 모두에서 악화. 사라진 정보는 리샘플링으로 안 돌아온다.

대신 위 표에서 보이듯 **평균 신뢰도가 심한 열화는 잡아낸다.**
그래서 고치는 대신 미리 경고한다.

| 신호 | good | fair | poor |
| --- | --- | --- | --- |
| 평균 신뢰도 | ≥ 0.94 | 0.87~0.94 | < 0.87 |
| 글자 높이 중앙값 | ≥ 20px | 14~20px | < 14px |

`poor`면 결과 상단에 빨간 배너로 "결과를 그대로 신뢰하지 마세요"를 띄우고,
해상도를 300dpi 이상으로 올리라고 안내한다.

### 신뢰도를 줄 단위로 믿으면 안 된다

위 표는 **페이지 단위**다. PDF 텍스트 레이어를 진짜 정답으로 놓고 줄 단위로 다시 쟀더니
(교재 PDF 3쪽 × 6조건 = 682줄) 훨씬 약했다.

```
정확   453줄 (66%)   평균 신뢰도 0.958
누락만  120줄 (18%)   평균 신뢰도 0.925
오독   109줄 (16%)   평균 신뢰도 0.916
```

방향은 맞지만 겹침이 심하다. **"확인 필요" 타일이 쓰던 임계값 0.75는 682줄 중 0줄을
잡았다 — 재현율 0%.** 열화를 걸어도 줄 신뢰도가 거기까지 안 내려간다.
화면에는 언제나 "0줄"이 떠 있었다.

| 임계값 | 표시 | 정밀도 | 재현율 | F1 |
| --- | --- | --- | --- | --- |
| 0.94 | 303줄 | 24% | 67% | 0.35 |
| **0.91** | **167줄** | **35%** | **53%** | **0.42** |
| 0.87 | 32줄 | 66% | 19% | 0.30 |
| 0.75 (예전) | **0줄** | 0% | 0% | — |

글자별 신뢰도의 최솟값(F1 0.35), 줄 길이 보정(0.39)도 시도했지만 더 나빴다.
**엔진이 주는 신호로는 0.43이 천장이다.**

그래서 임계값을 0.91로 올리고 이름을 `확인 필요` → `신뢰도 낮음`으로 바꿨다.
`확인 필요`는 "나머지는 맞다"로 읽히는데 재현율 53%로는 그렇게 쓸 수 없다.
경고문에도 한계를 적는다.

```
신뢰도 0.91 미만인 줄이 3개 있습니다. 먼저 확인해 보세요 —
다만 오인식의 약 절반은 이 목록에 안 잡히니 이것만 믿지는 마세요.
```

자세한 경위와 측정 함정은 [14번 문서](docs/troubleshooting/14-확인-필요-지표가-아무것도-못-잡았다.md).

## 여기서부터 디벨롭할 만한 지점

1. **손글씨·도장 겹침** — 합성으로 못 만들어서 실물 샘플이 필요하다. 유일하게 남은 미검증 영역.
2. **오류 예측 신호** — 신뢰도로는 F1 0.43이 천장이라는 걸 확인했다(위 참고).
   더 하려면 엔진 밖에서 신호를 찾아야 한다 — 사전 대조, 문맥 기반 이상 탐지 등.
3. **검출 누락 경고** — 오류의 18%가 "검출기가 아예 못 본" 글머리 기호·마침표다.
   신뢰도로는 원리적으로 못 잡는다. 검출 단계의 재현율을 따로 봐야 한다.
4. **추출 정확도 평가** — 지금은 근거 줄로 사람이 대조하는 수준. 정답 세트를 만들어
   항목별 정확도를 재야 실제 도입 판단이 선다.
5. **성능** — 페이지당 2~4초(CPU). 대량 처리하려면 배치 큐 + CoreML/GPU EP 필요.
   (`app/ocr.py`에서 `use_coreml` 활성화 실험 가능)
6. **저품질 입력 복구** — 전처리로는 안 된다는 걸 확인했다. 정말 살리려면
   초해상도 모델이나 더 큰 인식 모델(PP-OCRv5 server)이 필요하다.

## 알려진 제약

- 업로드 20MB, PDF 5쪽까지 (`backend/app/main.py`, `backend/app/ocr.py` 상단 상수)
- 긴 변 2000px로 축소 후 처리 — 반환되는 좌표도 축소된 이미지 기준이다
- 인증·저장 없음. 전부 메모리에서 처리하고 응답 후 버린다
