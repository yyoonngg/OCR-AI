# PDF 텍스트 레이어에서 줄이 쪼개지고 표가 안 잡힌다

- 날짜: 2026-08-17
- 대상: `backend/app/pdftext.py`
- 상태: 해결

## 배경

전자세금계산서·계약서·보고서처럼 프로그램이 만든 PDF에는 글자가 그대로 들어 있다.
그걸 이미지로 렌더해서 OCR하는 건 느리기만 하고 부정확하다. 실측:

| 방식 | 시간 | 결과 |
| --- | --- | --- |
| 텍스트 레이어 | **3.6ms** | `인가된 프로세스, 인가된 시스템만이` / `해야 한다는 원칙` |
| OCR | 6.77s | `인가된 프로세스 인가된 시스템만이` / `해야 한다는원칙` |

1,862배 느린데 쉼표를 놓치고 띄어쓰기가 붙는다. 그래서 텍스트 레이어를 우선 쓰기로 했다.

## 문제 1 — 표의 셀이 한 줄로 합쳐진다

`get_text_range()`가 주는 줄은 이렇게 나온다.

```
구분 개념
기밀성(Confidentiality) 오직 인가된 사람, ... 접근
```

라벨과 내용이 한 줄이다. 레이아웃 분석은 "한 줄 = 한 셀"을 전제로 하므로 표를 못 잡는다.

**해결**: 문자별 좌표(`get_charbox`)로 줄을 직접 재구성한다. 가로로 크게 벌어지면 셀을 끊는다.
임계값은 실제 문서의 간격 분포에서 뽑았다 (교재 PDF 1쪽, n=1045, 글자 높이 대비).

| | 중앙값 | 90% | 최대 |
| --- | --- | --- | --- |
| 붙어 있는 글자 | 0.03 | 0.11 | **0.30** |
| 공백 하나 | **0.53** | 0.69 | — |
| 표 셀 경계 | — | — | 2.99 이상 |

0.30과 0.53 사이(`SPACE_GAP = 0.35`)에서 공백을 넣고,
0.69와 2.99 사이(`COLUMN_GAP = 1.5`)에서 셀을 가른다.

처음에는 공백 임계값을 0.22로 뒀는데 붙은 글자(최대 0.30)를 갈라서
`보안 기 초강의 자료`가 나왔다. 분포를 재고서야 제대로 잡혔다.

## 문제 2 — 쉼표에서 줄이 끊긴다

셀은 갈렸는데 문장 한가운데가 끊겼다.

```
오직 인가된 사람, 인가된 프로세스
, 인가된 시스템만이 알 필요성에 근거하여 시스템에 접근
```

간격은 0.3px인데도 끊긴다. 좌표를 찍어 보니 원인이 나왔다.

```
글자      left   right     top  bottom     높이     겹침
스      540.3   552.8   319.4   330.5   11.1     11.1
,      553.1   554.7   330.5   333.4    2.9      0.0   ← 겹침 정확히 0
인      564.2   575.3   318.4   332.4   14.0      1.9
```

`get_charbox()`의 기본값은 **글자의 실제 잉크 범위**다. 쉼표는 baseline 근처에만 잉크가
있어서 top이 한글보다 12px 아래로 내려간다. 하필 `스`의 bottom(330.5)과 `,`의 top(330.5)이
정확히 같아 세로 겹침이 0이 됐다.

같은 쉼표라도 앞 글자가 `람`(bottom 332.6)이면 겹침이 1.9라 붙는다.
**글자마다 다르니 임계값으로는 못 막는다.**

**해결**: `get_charbox(i, loose=True)`. 폰트 라인박스라 같은 줄 글자가 **동일한 세로 범위**를
갖는다. 잉크 범위가 아니라 폰트 메트릭이라 쉼표도 한글과 같은 top/bottom이 나온다.

## 문제 3 — 표가 여전히 안 잡힌다

줄은 정확해졌는데(59줄, OCR과 동일) 표가 `2x2` 하나만 나왔다. 밴드를 찍어 봤다.

```
밴드2 top=318 bot=333  ['오직 인가된 사람, 인가된 프…']
밴드3 top=330 bot=346  ['기밀성(Confidentiality)']
밴드4 top=342 bot=357  ['해야 한다는 원칙']
```

셋이 각각 다른 밴드다. 라벨(330~346)과 첫 내용줄(318~333)의 겹침이 3px,
임계값(min높이 × 0.4 = 6)에 미달한다.

**표 셀에서 라벨이 세로 가운데 정렬**이라 실제로 어긋나 있다
([05번 문서](05-세로가운데정렬-라벨에서-행이-어긋난다.md)와 같은 상황).
OCR 경로에서는 검출 박스가 여유 있게 잡혀서 우연히 겹쳤을 뿐이다.

**해결**: 텍스트 레이어 줄의 bbox에 세로 여유를 준다(`LINE_PADDING = 0.2`).
OCR 검출 박스와 같은 성질을 줘야 같은 파이프라인을 태울 수 있다.

패딩을 처음에는 `_read_chars`에 넣었는데, 그러면 조각 병합 단계까지 영향을 받아
다른 행끼리 붙어 버렸다(59줄 → 47줄). **줄을 다 만든 뒤 bbox에만** 적용해야 한다.

| 패딩 | 1쪽 줄 수 | 1쪽 표 |
| --- | --- | --- |
| 0.0 | 59 | `2x2` |
| 0.10 | 59 | `3x2` |
| **0.15~0.40** | **59** | **`7x2`** ✅ |

0.15부터 안정적이라 여유를 두고 0.2로 정했다.

## 하마터면 지울 뻔한 코드

문자 순서 점프에 대비해 `_merge_fragments`(조각을 좌표로 다시 붙이는 단계)를 뒀는데,
교재 PDF에서 재보니 **59조각 → 59줄, 하는 일이 0이었다.** loose 박스가 근본 원인을
해결하면서 필요 없어진 것처럼 보였다.

지우기 전에 다른 PDF로 확인했다.

| PDF | 조각 → 줄 | 병합 |
| --- | --- | --- |
| 상세기획서 | 303 → 170 | **133개** |
| 홍보파일 | 100 → 92 | 8개 |
| 교재 | 59 → 59 | 0개 |

**한 파일만 보고 판단했으면 필요한 코드를 지웠다.** 레이아웃이 복잡한 문서일수록
문자 순서 점프가 잦다.

## 검증

```
텍스트 레이어 PDF (3쪽)   64.9ms   줄 125   표 7x2, 4x2   품질 good
같은 PDF 강제 OCR       27,120ms   줄 161   표 7x2, 2x2, 4x2
스캔 PDF                8,512ms   OCR 자동 폴백
```

**418배** 차이에 셀 내용도 더 정확하다. 이미지 경로는 회귀 없음
(sample/page0/twocol/table_only 전부 그대로).

테스트 8개: `backend/tests/test_pdftext.py`.
테스트를 처음 쓸 때 tight 박스 기준으로 데이터를 만들어 2개가 실패했다 —
**테스트가 실제 파이프라인과 다른 경로를 타고 있었다.** loose 박스 성질을 헬퍼에 반영해 고쳤다.

## 남은 것

- 회전된 페이지(`/Rotate`)는 검증하지 않았다. 좌표 변환이 어긋날 수 있다
- 세로쓰기 PDF는 대상이 아니다
- 텍스트 레이어가 부실한 PDF(글자 일부만 있는 하이브리드)는 글자 수 임계값
  (`MIN_CHARS_PER_PAGE = 40`)으로만 거른다. 더 정교한 판정이 필요할 수 있다
