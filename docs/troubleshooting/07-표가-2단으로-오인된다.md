# 표가 2단 편집으로 오인돼 세로로 쪼개진다

- 날짜: 2026-08-17
- 대상: `backend/app/layout.py` — `_column_layout`
- 상태: 해결 (단 폭 비율 조건)
- 제보: 사용자 직접 테스트

## 증상

표가 나오지 않고 라벨과 내용이 **따로따로 본문 블록**으로 나왔다.

```
[3] 본문 · 1단
    기밀성(Confidentiality)
    무결성(Integrity)
    가용성(Availability)
    인증성(Authentication)
    책임추적성(Accountability)

[4] 본문 · 2단
    개념

[5] 본문 · 2단
    오직 인가된 사람, 인가된 프로세스 ...
    정보의 내용이 불법적으로 생성 또는 ...
    정당한 사용자가 정보시스템의 데이터 ...
```

## 원인

블록 라벨의 `·1단`, `·2단`이 결정적 단서였다. 표가 끊긴 게 아니라
**단 나누기가 표를 세로로 두 동강 낸 것**이다.

단 판정 조건은 다음과 같았다.

| 조건 | 표의 두 열은? |
| --- | --- |
| 각 단에 줄 3개 이상 | 통과 (7줄) |
| 각 단이 영역 높이의 60% 이상 | 통과 (표 전체 높이) |
| 각 단의 줄 길이 중앙값 ≥ 8자 | **통과** ← 여기가 구멍 |

`기밀성(Confidentiality)`는 22자다. 표의 라벨 열이라도 한글+영문 병기라
**"본문처럼 길다" 조건을 그냥 통과**해 버린다.
`수량`·`금액` 같은 짧은 열만 걸러내고 있었던 것이다.

## 재현이 까다로웠던 이유

같은 페이지를 잘라낸 다른 크롭에서는 재현되지 않았다.
크롭에 `보기` 상자가 포함되면 그 안의 긴 줄들이 단 사이 여백을 가로질러
"가로지르는 줄 8% 이하" 조건에 걸려 **우연히** 막혔기 때문이다.

결국 가드를 임시로 끄고(`MAX_COLUMN_WIDTH_RATIO = 99`) 표만 잘라낸 크롭에
여백을 60px 벌려 직접 호출해서, 제보와 똑같은 분할을 재현했다.

```
단0: 구분 / 기밀성(Confidentiality) / 무결성(Integrity) / ...
단1: 개념 / 오직 인가된 사람 ... / 정보의 내용이 ... / ...
```

## 해결 — 단 폭 비율

**2단 편집은 설계상 단 폭이 거의 같다.** 표는 라벨 열이 내용 열보다 훨씬 좁다.

| | 단 폭 | 비율 |
| --- | --- | --- |
| 2단 편집 테스트 문서 | 325px / 316px | **1.03배** |
| 정보보호 목표 표 | 157px / 550px | **3.50배** |

폭은 구분선(가운데 정렬 제목)을 뺀, 가드가 실제로 보는 값이다.
`_column_layout`에 직접 넣어 측정했다.

```python
MAX_COLUMN_WIDTH_RATIO = 1.8
if max(widths) / min(widths) > MAX_COLUMN_WIDTH_RATIO:
    return None
```

## 검증

12개 입력 전부 통과. 특히 여백을 벌려 다른 조건을 모두 통과시켜도 이 조건에서 막힌다.

```
sample.png       단=1  표=['5x2', '4x4', '3x2']
page0.png        단=1  표=['7x2', '5x3']
table_only.png   단=1  표=['7x2']
crop 변형 4종     단=1  표=['7x2', '5x3']
twocol.png       단=2  표=[]            ← 진짜 2단은 그대로
```

## 배운 것

- **"글자 길이"는 표 열과 본문 단을 가르는 신호가 아니다.** 기하(폭 비율)가 훨씬 안정적이다
- 재현이 안 될 때는 가드를 임시로 꺼서 실패 경로를 역으로 확인하는 게 빠르다
- 크롭 범위·해상도가 조금만 달라도 검출 결과가 달라진다. **제보된 원본 파일을 받는 게 최선이다**

## 남은 것

- 폭이 크게 다른 2단 편집(좁은 사이드바 + 넓은 본문)은 놓친다.
  단을 놓치는 쪽이 표를 부수는 쪽보다 피해가 작다고 보고 이렇게 뒀다
