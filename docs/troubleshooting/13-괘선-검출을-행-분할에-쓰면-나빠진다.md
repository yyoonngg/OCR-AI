# 괘선을 행 분할에 쓰면 오히려 나빠진다

- 날짜: 2026-08-17
- 대상: `backend/app/rules.py` (신규), `backend/app/layout.py`
- 상태: 해결 (범위를 줄여서)

## 배경

표 판정이 전부 글자 좌표 추측이라 임계값이 계속 늘었다.

```
MAX_COLUMN_WIDTH_RATIO   1.8   (07번)
MIN_COLUMN_TEXT_LENGTH   8     (03번)
CHOICE_REPEAT_RATIO      0.6   (09번)
HEADER_LENGTH_RATIO      0.5
_try_add 열 구조 유지          (04번 → 06번 회귀)
_rows_of 첫 열 앵커            (05번)
```

표에 실제로 그어진 선을 보면 이 추측을 상당수 걷어낼 수 있을 것 같았다.
특히 `_rows_of`의 "가장 가까운 앵커에 붙인다"는 04·05·06번이 전부 나온 자리다.
**결론부터 쓰면, 행 분할을 괘선에 맡기는 건 실패했다.** 표 판정 보강만 남겼다.

## 문제 1 — Otsu로는 괘선이 안 보인다

`spacing.py`가 쓰는 Otsu 이진화를 그대로 가져다 썼더니 거의 안 잡혔다.

```
거래명세서 샘플   가로 1개, 세로 0개
교재 1쪽         가로 2개, 세로 1개
교재 3쪽         가로 0개
표만 크롭         가로 0개, 세로 1개   ← 표인데 0개
```

교재 1쪽 표 영역의 행별 평균 밝기를 찍어 보니 선은 있었다.

```
y=361  242
y=362  186   ← 한 줄만 뚝 떨어진다 = 괘선
y=370  236
y=476  186   ← 괘선
y=511  186   ← 괘선
```

**밝기 186~234짜리 1px 연한 회색 선**이다. Otsu는 글자(검정)와 배경(흰색)
사이에서 임계값을 잡으므로 그 중간의 연한 선이 배경 쪽으로 떨어진다.

**해결**: "배경 중앙값보다 `DARK_DELTA`만큼 어두운가"로 바꿨다.

```
             Otsu    배경 대비 -12
거래명세서      1개  →   5개
교재 1쪽        2개  →   9개
교재 3쪽        0개  →   4개
표만 크롭       0개  →   7개
```

노이즈가 같이 들어오지만 가로로 긴 커널로 opening을 걸면 글자와 함께 지워진다.

## 문제 2 — 기준을 이미지 크기로 잡으면 양쪽에서 틀린다

두께·길이 조건을 이미지 변 대비로 걸었더니 반대 방향으로 두 번 틀렸다.

**두꺼운 쪽**: 거래명세서 샘플은 스캔 시뮬레이션(블러+노이즈)이 걸려 있다.
1px로 그린 선이 실제로는 이렇게 퍼져 있다.

```
y=523  최소=230  (배경 242)
y=524  최소=202   ← 여기부터
y=529  최소=198
y=533  최소=193
y=534  최소=207   ← 여기까지, 두께 10~15px
y=535  최소=230
```

"이미지 높이의 0.5%"(8px) 상한에 걸려 **거래명세서 괘선이 전부 버려졌다.**

**얇은 쪽**: 표만 크롭은 857x292라 최소 길이가 43px밖에 안 됐다.
한글 세로획이 그걸 넘어서 **세로선 70개가 잡혔고 전부 오검출이었다.**

**해결**: 기준을 글자 높이로 바꿨다. 괘선은 블러가 걸려도 글자보다 얇고
글자 획보다 훨씬 길다.

```
MAX_THICKNESS_HEIGHTS  1.0   블러 괘선 0.75배 통과 / 머리글 색 배경 2.1배 차단
MIN_LENGTH_HEIGHTS     3.0   글자 세로획 차단
SEED_HEIGHTS           1.5   opening 커널
```

`detect(image, text_height)`로 페이지 글자 높이 중앙값을 받는다.

## 시도했지만 안 된 것 — 괘선으로 행 나누기

여기가 원래 목표였다. 오검출을 거르려고 "표 폭의 90% 이상을 덮는 선만 행 구분선으로
본다"는 조건을 붙였다. 이 조건 자체는 잘 갈렸다 (진짜 100% 이상 / 오검출 80%, 34%).

그 선들로 행을 나눠 현재 결과와 비교했다.

| 표 | 현재 (정답) | 괘선 기반 |
| --- | --- | --- |
| page0 7x2 | 7행 | **6행** |
| page2 4x2 | 4행 | **3행** |
| table_only 7x2 | 7행 | **6행** |
| sample 4x4 | 4행 | **3행** |

**5개 표 중 4개가 나빠졌다.** 증상이 전부 같다.

```
현재:  r0: 구분 | 개념
       r1: 기밀성(Confidentiality) | 오직 인가된 사람, 인가된 프로세스…

괘선:  r0: 기밀성(Confidentiality) | 구분 | 오직 인가된 사람… | 개념
```

**머리글 행이 선이 아니라 색 배경 띠로 구분돼 있다.** 띠는 글자 높이의 2.1배라
두께 조건에서 (옳게) 걸러지고, 그러면 머리글 경계에 괘선이 없다.
page2에서는 띠가 두께 25px(글자 26px)로 아슬아슬하게 통과했는데,
그 중심선이 머리글 글자 한가운데를 관통해서 더 나빴다.

띠의 위아래 모서리를 경계로 쓰는 방법도 있지만, 그건 "괘선 인식"이 아니라
배경색 분할이라 다른 문제다. 여기서 멈췄다.

결정적으로, **거래명세서의 5x2 표는 괘선이 0개다.** 없다고 표가 아닌 게 아니다.
괘선은 양방향 신호가 아니다.

## 해결 — 한 방향으로만 쓴다

**괘선이 표를 가로지르면 그건 확실히 표다. 없을 때는 아무 말도 하지 않는다.**

가로지르는 괘선 개수를 실측했다.

```
괘선 있는 표   4x4 거래명세서 3개 / 4x2 교재 4개 / 7x2 교재 6개, 6개
괘선 없는 표   5x2 거래명세서 0개 / 3x2 합계표 1개 (위 표의 아래 테두리가 걸친 것)
```

3에서 깨끗이 갈려서 `MIN_RULES_FOR_TABLE = 3`으로 잡았다. 1~2로 내리면
상자 하나 두른 4지선다가 위아래 테두리 2개로 표가 되어 버린다.

쓰는 자리는 한 곳이다. 4지선다 판정을 뒤집는다.

```python
if table.rows >= 2 and table.columns >= 2 and (
    _is_ruled(table.bbox, rulings, page_height)
    or not _is_choice_list(table, previous)
):
```

`_is_choice_list`는 항목 번호·앞 블록의 물음표·값 반복이라는 내용 신호에 기댄다
([09번](09-4지선다가-표로-잡힌다.md)). 값이 반복되는 진짜 표가 문제 문장 뒤에 오면
잘못 강등되는데, 그려진 선이 그보다 확실한 증거다.

## 검증

전체 샘플에서 **블록 구조가 한 글자도 바뀌지 않았다.** 괘선을 넘긴 경우와
넘기지 않은 경우를 블록 단위로 비교했다.

```
sample.png / page0 / page2 / twocol / table_only        차이 없음
opt_hi / opt_lo / opt_nomark (4지선다 재현본)            차이 없음
lecture3.pdf (텍스트 레이어)                             차이 없음
```

4지선다는 그대로 강등된다. 가드가 기존 판정을 침범하지 않는다는 뜻이다.

검출 비용:

```
sample.png      26.4ms
page0.png       15.0ms
table_only.png   1.9ms
lecture3.pdf    43.6ms (3쪽)
```

텍스트 레이어 PDF는 27ms → 72ms로 **2.6배 느려졌다.** 절대값이 작아서 두었지만,
텍스트 레이어 경로에서 괘선이 벌어 주는 게 아직 없다는 건 사실이다.

테스트 8개(`backend/tests/test_rules.py`) + 레이아웃 3개.
레이아웃 쪽은 **가드가 실제로 작동하는지**를 본다 — 괘선을 안 주면 목록으로 강등되고
3개를 주면 표가 되는 것을 같은 입력으로 확인한다. 안 그러면 죽은 코드인지 알 수 없다.

## 남은 것

- **행 분할은 여전히 좌표 휴리스틱이다.** 04·05·06번의 근본 원인은 그대로다.
  괘선으로 고치려면 색 배경 띠를 행 경계로 인정하는 작업이 먼저다
- **셀 병합(rowspan)은 여전히 불가능하다.** 원래 이걸 노렸는데 행 분할을
  포기하면서 같이 빠졌다
- **세로 괘선은 사실상 못 쓴다.** 교재 1쪽에서 가로 8개에 세로 1개인데
  그 1개도 표가 아니라 페이지 가장자리 장식선이다
- **기울어진 스캔은 미검증.** 선이 대각선이면 가로 커널에 안 걸려 조각나고
  길이 조건에 미달한다. [10번](10-CER-지표가-순서를-오류로-셌다.md)에서 기울기가
  인식률에는 영향이 없다고 확인했지만 괘선 검출은 다르다
- `DARK_DELTA = 12`는 흰 종이 기준이다. 누런 스캔지나 배경색이 있는 문서는 미검증
