## 여기서 반복해서 나온 교훈

- **레이아웃은 임계값에 기댄다. 한쪽을 완화하면 다른 쪽이 깨진다.**
  04 → 06이 그 예다. 그래서 `backend/tests/test_layout.py`를 붙였다.
- **저해상도에서 통과했다고 안심하면 안 된다.** 05는 크롭에서는 완벽했고
  전체 페이지 해상도에서만 드러났다.
- **글자 길이 같은 내용 기반 신호보다 기하(폭·간격 비율)가 안정적이다.** (07)
  단, **기하로 안 되는 것도 있다.** 4지선다는 격자 배치가 표와 완전히 같아서
  좌표에 답이 없고, 항목 번호(`①②③④`)라는 내용 신호로만 갈린다. (09)
- **재현이 안 되면 가드를 임시로 꺼서 실패 경로를 역으로 확인한다.** (07)
- **크롭 범위·해상도가 조금만 달라도 검출 결과가 달라진다.**
  제보를 받으면 원본 파일부터 확보하는 게 가장 빠르다.
- **지표가 측정하려는 걸 측정하는지 먼저 검증하라.** 10번은 잘못된 CER 때문에
  "기울기가 최악"이라는 정반대 결론이 나올 뻔했다. 다른 지표와 어긋나면(신뢰도는
  그대로인데 CER만 높다) 그게 단서다. 숫자가 이상하면 원본 출력을 diff 해봐라.
- **"이렇게 하면 되겠지"를 검증 없이 믿지 마라.** 11번의 업스케일·언샤프는
  자연스러운 발상이었지만 측정해보니 개선이 없거나 악화였다. 재는 데 10분 걸렸다.
- **한 파일로 판단하지 마라.** 12번에서 병합 단계가 "하는 일이 0"으로 보여 지울 뻔했는데,
  다른 PDF에서는 303조각을 170줄로 붙이고 있었다.
- **테스트도 실제 경로를 타는지 확인하라.** 12번 테스트를 tight 박스 기준으로 썼더니
  실제 파이프라인(loose 박스)과 다른 경로를 타서 통과할 수 없는 테스트가 됐다.
- **"내 이미지에서 됐다"는 해결이 아니다.** 09는 내 렌더에서만 마커가 검출돼
  통과했고 제보자 환경에서는 그대로 실패했다. 실패 조건을 인위적으로 만들어
  (마커를 흰색으로 덮는 식으로) 재현해 보는 게 빠르다.
- **새 신호를 넣기 전에 그게 기존 결과를 이기는지부터 재라.** 13번의 괘선은
  당연히 좌표보다 나을 것 같았는데, 행 분할에 써 보니 5개 표 중 4개가 나빠졌다.
  신호가 양방향인지도 확인해야 한다 — 괘선은 "있으면 표"만 참이고
  "없으면 표 아님"은 거짓이다(거래명세서 5x2 표는 괘선이 0개).
- **임계값은 이미지 크기가 아니라 글자 높이로 잡아라.** 13번에서 이미지 변 대비로
  걸었더니 큰 스캔본에서는 두꺼워진 선을 버리고, 작은 크롭에서는 글자 획을 선으로
  주웠다. 같은 실수가 양쪽 방향으로 났다.
- **화면에 띄우는 숫자는 그게 맞는지 재고 나서 띄워라.** 14번의 "확인 필요 0줄"은
  임계값이 실전 분포보다 훨씬 낮아서 **언제나 0줄**이었다. 지표가 죽어 있어도
  화면은 멀쩡해 보인다 — 오히려 안심시키는 쪽으로 틀린다.
- **정답이 정말 정답인지부터 봐라.** 14번에서 PDF 텍스트 레이어를 정답으로 썼는데
  수식은 사설 영역 코드라 깨져 있었고(OCR 쪽이 맞았다), 도표 글자는 아예 없었다.
  정답을 의심 없이 쓰면 멀쩡한 결과가 오류로 집계된다.
